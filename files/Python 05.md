### Exercise 0: Data Processor (Процессор данных)

| Параметр | Значение |
|---|---|
| **Директория** | `ex0/` |
| **Файл** | `data_processor.py` |
| **Разрешено** | builtins, стандартные типы, `import typing`, `import abc` |

#### Что нужно сделать
Построить **базовую архитектуру** обработки данных:

1. **`DataProcessor`** (абстрактный класс, наследуется от `ABC`):
   - Абстрактный метод `validate(data)` — проверяет, подходят ли данные для этого процессора
   - Абстрактный метод `ingest(data)` — обрабатывает входные данные
   - Метод `output(nb)` — возвращает `nb` обработанных элементов (список кортежей `(index, str_value)`)
   - Внутренний буфер для хранения обработанных данных

2. **Три специализированных класса:**
   - `NumericProcessor` — обрабатывает числовые списки `[3.14, -1, 2.71]`
   - `TextProcessor` — обрабатывает строки и списки строк
   - `LogProcessor` — обрабатывает списки словарей с ключами `log_level` и `log_message`

Каждый переопределяет `validate()` и `ingest()`.

#### 💡 Подсказки
1. Абстрактный класс:
   ```python
   from abc import ABC, abstractmethod
   
   class DataProcessor(ABC):
       @abstractmethod
       def validate(self, data):
           pass
       
       @abstractmethod
       def ingest(self, data):
           pass
   ```
2. **Нельзя** создать экземпляр абстрактного класса напрямую: `DataProcessor()` → ошибка
3. `validate()` должен проверять **тип** данных (isinstance)
4. `ingest()` принимает данные, валидирует и **добавляет** в внутренний буфер
5. `output(nb)` — **извлекает** (pop) `nb` элементов из буфера и возвращает их

> ⚠️ **Нюанс:** `output()` должен возвращать `list[tuple[int, str]]` — список кортежей `(порядковый_номер, строковое_представление)`. Это будет использоваться в ex2 для экспорта.

### Exercise 1: Polymorphic Processing (Полиморфная обработка потока)

| Параметр | Значение |
|---|---|
| **Директория** | `ex1/` |
| **Файл** | `data_stream.py` |
| **Разрешено** | builtins, стандартные типы, `import typing`, `import abc` |

#### Что нужно сделать
Создать класс **`DataStream`**, который объединяет все процессоры:

1. `register_processor(proc: DataProcessor)` — регистрирует процессор
2. `process_stream(stream: list[typing.Any])` — анализирует каждый элемент потока и **направляет** его к подходящему зарегистрированному процессору. Если ни один не подходит — выводит ошибку
3. `print_processors_stats()` — статистика: сколько элементов обработал каждый процессор

#### Пример
```python
stream = ['Hello world', [3.14, -1, 2.71], 
          [{'log_level': 'WARNING', 'log_message': '...'}], 
          42, ['Hi', 'five']]
```
- `NumericProcessor` возьмёт `[3.14, -1, 2.71]` и `42` (если реализуешь int→list)
- `TextProcessor` возьмёт `'Hello world'` и `['Hi', 'five']`
- `LogProcessor` возьмёт список словарей с логами

#### 💡 Подсказки
1. В `process_stream()` для каждого элемента итерируй по зарегистрированным процессорам
2. Вызывай `proc.validate(element)` — если `True`, отдай на `proc.ingest(element)`
3. Если **ни один** процессор не подходит — напечатай ошибку
4. Это и есть **полиморфизм**: один и тот же вызов `validate()` ведёт себя по-разному для разных процессоров

### Exercise 2: Data Pipeline (Пайплайн данных — Duck Typing)

| Параметр | Значение |
|---|---|
| **Директория** | `ex2/` |
| **Файл** | `data_pipeline.py` |
| **Разрешено** | builtins, стандартные типы, `import typing`, `import abc` |

#### Что нужно сделать
Расширить DataStream **плагинной системой экспорта** с помощью duck typing:

1. **`ExportPlugin`** — класс, наследующийся от `Protocol` (из `typing`):
   ```python
   class ExportPlugin(Protocol):
       def process_output(self, data: list[tuple[int, str]]) -> None: ...
   ```
   Это определяет **интерфейс**: любой класс с методом `process_output` — совместим

2. **`DataStream.output_pipeline(nb, plugin)`** — вызывает `output(nb)` у всех процессоров, затем передаёт результаты в `plugin.process_output()`

3. Создать **минимум два плагина:**
   - `CSVExportPlugin` — выводит данные в CSV формате (вручную, без `import csv`)
   - `JSONExportPlugin` — выводит данные в JSON формате (вручную, без `import json`)

#### Пример
```
Send 3 processed data from each processor to a CSV plugin:
CSV Output:
3.14,-1,2.71
CSV Output:
Hello world,Hi,five
CSV Output:
WARNING: Telnet access! Use ssh instead,INFO: User wil is connected

Send 5 processed data to a JSON plugin:
JSON Output:
{"item_3": "42", "item_4": "21", ...}
```

#### 💡 Подсказки
1. **`Protocol`** (из `typing`) — это **duck typing** на уровне типов. Не нужно наследоваться от `ExportPlugin` — достаточно реализовать метод `process_output`
2. CSV вручную: `",".join([str_value for _, str_value in data])`
3. JSON вручную: `'{"' + '", "'.join([f'item_{idx}": "{val}' for idx, val in data]) + '}'`
4. `output_pipeline` вызывает `output(nb)` у каждого зарегистрированного процессора

> ⚠️ **Нюанс:** Duck typing vs наследование: `Protocol` — это «если оно ходит как утка и крякает как утка, то это утка». Плагину не нужно знать про `ExportPlugin` — ему достаточно иметь метод `process_output`. Это используется в реальных системах (Django, Flask и т.д.).

> ⚠️ **Нюанс:** Формат `data` — `list[tuple[int, str]]`, где `int` — порядковый номер элемента за всё время работы процессора (не сбрасывается).

```
ex0: ABC + абстрактные методы (validate/ingest/output)
 │   → Три специализированных процессора
 │
 ▼
ex1: DataStream — полиморфная маршрутизация данных

```

Этот модуль показывает, как строить **расширяемые системы**: добавить новый тип данных = добавить новый процессор. Добавить новый формат экспорта = добавить новый плагин. Основной код **не меняется**.
